# 代码审核 (Code Review + BDD)

作为专业代码审核员，对代码进行质量审查，从安全性、性能、正确性、可维护性、测试覆盖等多维度发现潜在问题并提供改进建议。

## 审核流程

```
1. 理解代码上下文 → 2. 检查安全性 → 3. 检查性能 → 4. 检查正确性 → 5. 检查可维护性 → 6. 检查测试覆盖 → 7. 汇总反馈
```

## 问题严重等级

| 等级 | 标识 | 说明 |
|------|------|------|
| 严重 | 🔴 | 必须修复，可能导致系统崩溃、安全问题或数据丢失 |
| 警告 | 🟡 | 建议修复，可能导致性能下降或维护困难 |
| 建议 | 🟢 | 可选优化，提升代码质量 |

## 1. 安全性检查 🔒

### 常见安全漏洞

```
🔴 SQL 注入
   风险: 用户输入直接拼接到 SQL 语句
   示例: query = "SELECT * FROM users WHERE id=" + userId
   修复: 使用参数化查询或 ORM

🔴 XSS (跨站脚本攻击)
   风险: 未转义的用户输入直接输出到 HTML
   示例: element.innerHTML = userInput
   修复: 使用 textContent 或转义函数

🔴 敏感信息泄露
   风险: 密钥、密码、Token 硬编码或打印到日志
   示例: const API_KEY = "sk-xxxx"
   修复: 使用环境变量或密钥管理服务

🔴 命令注入
   风险: 用户输入直接用于系统命令
   示例: exec("rm " + filename)
   修复: 避免使用 shell 执行，或严格验证输入

🔴 不安全的依赖
   风险: 使用已知漏洞的第三方库
   修复: 定期更新依赖，使用安全扫描工具

🔴 越权访问
   风险: 缺少权限校验或校验不完整
   修复: 每个接口显式校验权限
```

### 权限校验清单

```
□ 认证校验: 用户是否已登录
□ 授权校验: 用户是否有权访问该资源
□ 参数校验: 所有用户输入是否经过验证
□ 敏感操作: 是否有审计日志
```

## 2. 性能检查 ⚡

### 常见性能问题

```
🟡 算法复杂度
   风险: 循环嵌套或低效算法
   检查: O(n²) 或更差的代码
   优化: 空间换时间、使用索引、使用缓存

🟡 内存泄漏
   风险: 未释放的资源、闭包引用、事件监听未移除
   检查: 全局变量增长、定时器未清理
   修复: 及时清理、使用 WeakMap/WeakSet

🟡 N+1 查询问题
   风险: 循环中执行数据库查询
   示例: for item in items: db.query(item.id)
   修复: 批量查询或预加载

🟡 重复计算
   风险: 相同计算执行多次
   修复: 缓存结果、使用记忆化

🟡 同步阻塞
   风险: 在主线程执行耗时操作
   修复: 异步处理、使用 Web Worker

🟡 资源未释放
   风险: 文件句柄、数据库连接未关闭
   检查: 是否使用 try-finally 或 context manager
```

### 性能检查清单

```
□ 数据库查询是否有效率
□ 是否有不必要的重复计算
□ 是否有内存泄漏风险
□ 大数据处理是否分批进行
□ 是否合理使用缓存
□ 循环中是否有性能陷阱
```

## 3. 正确性检查 ✅

### 常见逻辑错误

```
🔴 空指针/空引用
   风险: 访问 null 或 undefined 的属性
   检查: 返回值、API 响应、DOM 元素是否为空
   防御: 可选链(?.)、空值合并(??)、默认值

🟡 边界条件
   风险: 未处理极端情况
   示例: 数组越界、负数、除零、溢出
   检查: 0、空数组、负数、最大值、最小值

🟡 竞态条件
   风险: 多线程/异步操作导致的不一致
   检查: 共享状态访问、文件写入
   修复: 使用锁、原子操作、事务

🔴 错误处理
   风险: 异常被吞掉或处理不当
   检查: try-catch 是否正确、是否记录错误
   修复: 适当的错误传播、用户友好的错误信息

🟡 类型错误
   风险: 类型不匹配导致的运行时错误
   检查: TypeScript 类型、类型断言
   修复: 启用严格模式、添加类型守卫
```

### 正确性检查清单

```
□ 所有外部输入是否验证
□ 边界条件是否处理
□ 错误是否被正确处理和记录
□ 异步操作是否正确处理竞态
□ 类型转换是否安全
□ 是否有死代码或无法到达的代码
```

## 4. 可维护性检查 📝

### 代码异味

```
🟡 重复代码
   风险: 相同逻辑多处复制
   修复: 提取函数或使用继承/组合

🟡 过长函数
   风险: 函数超过 50 行，难以理解
   修复: 拆分为多个小函数

🟡 过深嵌套
   风险: 嵌套超过 3 层
   修复: 提取函数、使用卫语句、合并条件

🟡 命名不当
   风险: 变量/函数命名不清晰
   检查: 是否使用有意义的名称、是否符合规范

🟡 魔法数字/字符串
   风险: 代码中出现硬编码的数值或字符串
   修复: 定义常量或配置

🟡 注释缺失或过时
   风险: 复杂逻辑没有解释
   检查: 注释是否准确、是否需要更新
```

### 可维护性检查清单

```
□ 代码是否遵循项目规范
□ 命名是否清晰一致
□ 是否有重复代码
□ 函数长度是否合理
□ 是否有魔法数字/字符串
□ 注释是否必要且准确
□ 模块间耦合是否合理
```

## 5. 测试覆盖检查 🧪

### 测试策略检查

```
🔴 无测试或测试缺失
   风险: 核心业务逻辑无保护，修改极易引入 bug
   检查: 是否有测试文件，测试文件与代码比例
   修复: 按测试金字塔补充测试

🔴 测试不通过
   风险: 测试被破坏或从未运行
   检查: CI 是否执行测试，测试是否通过
   修复: 修复或删除废弃测试

🟡 测试覆盖率不足
   风险: 关键路径未被测试覆盖
   检查: 覆盖率报告，低于 80% 需关注
   修复: 补充边界条件、异常路径测试
```

### 测试质量检查

```
🟡 单元测试质量
   风险: 测试依赖实现细节，而非行为
   检查: 测试是否 mock 内部方法、访问私有属性
   修复: 基于 public API 测试，关注输入输出

🟡 集成测试缺失
   风险: 组件间集成问题无法发现
   检查: 是否有 API、数据库、消息队列集成测试
   修复: 补充关键路径的集成测试

🟡 测试数据硬编码
   风险: 测试与实现耦合，脆弱
   检查: 是否使用 Test Data Builder、Fixture
   修复: 使用数据工厂生成测试数据
```

### AAA 模式检查

```
□ Arrange: 测试数据准备是否清晰
□ Act: 执行动作是否单一
□ Assert: 断言是否明确，验证单一行为

□ 测试命名是否描述场景而非实现
□ 测试是否遵循 Given-When-Then 结构
□ 是否有 Setup/Teardown 清理资源
```

### Mock 滥用检查

```
🔴 过度 Mock
   风险: Mock 内部实现，测试变成白盒测试
   检查: 是否 mock 了被测类的依赖
   修复: 使用真实对象或只 mock 外部依赖

🔴 Mock 验证过度
   风险: 测试验证方法调用次数而非结果
   检查: 是否使用 verify(mock, times(n))
   修复: 关注最终结果，而非中间调用

🟡 Mock 静态方法
   风险: 静态方法难以测试，影响代码设计
   检查: 是否大量 mock 静态方法
   修复: 考虑封装为可注入的依赖
```

## 5.1 BDD 行为驱动测试审核 🔍

### BDD 测试覆盖检查

```
🟡 BDD Feature 文件缺失
   风险: 业务需求与实现之间缺少可追溯性
   检查: 核心业务功能是否有对应的 .feature 文件
   修复: 为关键业务场景编写 Gherkin Feature

🟡 场景覆盖不足
   风险: 只覆盖"阳光路径"，忽视边界和异常
   检查: Feature 中是否有 Scenario Outline 和 Examples
   修复: 添加边界值和异常场景

🟡 Step Definitions 缺失
   风险: Feature 无法执行，测试不可运行
   检查: 每个 Given/When/Then 是否有对应实现
   修复: 补充 Step Definitions
```

### BDD 场景质量审核

```
┌─────────────────────────────────────────────────────────────┐
│           BDD 场景审核清单                                   │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ✅ Scenario 命名规范                                        │
│     - 使用业务语言，非技术术语                                │
│     - 描述 "做什么" 而非 "怎么做"                              │
│     - 示例: "用户使用有效邮箱注册" 而非 "调用 POST /users"     │
│                                                             │
│  ✅ Given 上下文清晰                                         │
│     - 明确设置测试前置条件                                   │
│     - 避免过于复杂的准备步骤（考虑使用 Background）            │
│     - 使用真实业务数据                                       │
│                                                             │
│  ✅ When 操作明确                                           │
│     - 描述单一用户操作或系统事件                              │
│     - 避免多个 When 合并（考虑拆分为多个场景）                 │
│                                                             │
│  ✅ Then 结果可验证                                         │
│     - 断言应该是可自动验证的                                 │
│     - 避免 "Then 用户应该满意" 这类模糊断言                   │
│                                                             │
│  ✅ Examples 参数化                                         │
│     - 使用 Scenario Outline 覆盖多组数据                      │
│     - 边界值和等价类应被覆盖                                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### BDD Feature 文件审核示例

```gherkin
# ✅ 良好示例 - 业务语言清晰
Feature: 用户提现功能

  Scenario: 用户成功提现到绑定银行卡
    Given 用户 "Alice" 已登录
    And 用户余额为 ¥10000
    And 用户已绑定银行卡 "****1234"
    When 用户申请提现 ¥5000
    Then 提现申请状态应为 "处理中"
    And 用户余额应减少 ¥5000
    And 用户应收到提现通知

# ❌ 不良示例 - 技术术语、业务逻辑缺失
Feature: 提现API

  Scenario: 调用提现接口
    Given 用户已登录
    When 调用 POST /api/withdraw
    Then 返回 200
```

### BDD 与代码实现对齐审核

```
🔴 场景与实现脱节
   风险: Feature 描述的功能代码中未实现
   检查: 每个 Scenario 是否在代码中有对应逻辑
   修复: 确保测试与实现同步

🔴 业务规则不一致
   风险: Gherkin 描述的业务规则与代码逻辑不符
   检查: 验证条件、计算逻辑是否一致
   修复: 统一业务规则定义

🟡 数据模型映射缺失
   风险: Step 中使用的数据与领域模型不一致
   检查: Given/When/Then 中的数据是否对应领域实体
   修复: 使用领域术语定义测试数据
```

### BDD 测试文件结构审核

```
src/
├── tests/
│   ├── bdd/
│   │   ├── features/              # Feature 文件 (需求规范)
│   │   │   ├── login.feature
│   │   │   ├── checkout.feature
│   │   │   └── order-management.feature
│   │   ├── step-definitions/      # Step 实现
│   │   │   ├── login.steps.ts
│   │   │   ├── checkout.steps.ts
│   │   │   └── world.ts          # 共享上下文
│   │   ├── support/               # 辅助配置
│   │   │   ├── hooks.ts          # Before/After 钩子
│   │   │   └── transforms.ts     # 自定义类型转换
│   │   └── cucumber.js           # Cucumber 配置
│   └── unit/                     # TDD 单元测试
│       └── ...

审核要点:
□ Feature 文件是否按业务领域组织
□ Step Definitions 是否与 Feature 一一对应
□ 是否有共享的 World/Context 类
□ hooks.ts 是否处理测试生命周期
□ cucumber.js 配置是否正确
```

### BDD 测试报告审核

```
🟡 测试报告缺失
   风险: 无法追踪测试执行情况
   检查: CI 是否有 BDD 测试报告
   修复: 配置 JSON/HTML 报告输出

🟡 失败场景难以复现
   风险: 测试失败后难以定位问题
   检查: 失败时是否自动截图、记录上下文
   修复: 在 After hook 中添加截图和日志

🟡 场景超时未处理
   风险: 异步操作导致场景假失败
   检查: 是否有合理的超时配置
   修复: 设置合理的 defaultTimeout
```

## 6. 最佳实践检查 🏆

### SOLID 原则

```
🟢 单一职责 (SRP)
   每个类/模块只有一个变更原因

🟢 开闭原则 (OCP)
   对扩展开放，对修改关闭

🟢 里氏替换 (LSP)
   子类可以替换基类而不破坏程序

🟢 接口隔离 (ISP)
   使用小而专注的接口

🟢 依赖倒置 (DIP)
   依赖抽象而非具体实现
```

### Git 提交规范

```
□ 提交信息是否清晰描述改动
□ 是否是小而独立的提交
□ 提交消息是否符合 Conventional Commits
□ 是否包含必要的测试
```
